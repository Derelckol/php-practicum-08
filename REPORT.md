# Звіт до практичної роботи №8

**Дисципліна:** «Сучасні технології розробки WEB-застосувань мовою програмування PHP».  
**Тема:** Безпека PHP-застосунків: пошук і усунення типових вразливостей.  
**Варіант 15:** Система бронювання квитків (кіно/події).

## 1. Мета роботи

Провести аудит практичних робіт №1–7 на SQL Injection, XSS, CSRF та незахищені операції зміни даних; усунути виявлені недоліки у фінальній версії й перевірити результат. Цільові елементи варіанта 15 — фільтр `venue`, поле `title` та купівля квитка зі зміною `seats_left`.

## 2. Хід роботи та обсяг аудиту

1. Досліджено структуру робіт №1–7, джерела даних, HTML-форми, SQL-запити й API.
2. Перевірено параметризацію SQL та місця виведення назв подій.
3. Додано сесійний CSRF-захист операцій зміни даних.
4. Перевірено HTTP-методи, повторне надсилання покупки та атомарність зміни залишку.
5. Уніфіковано серверну валідацію та обробку винятків.
6. Виконано перевірку синтаксису, HTTP-тести з MySQL та конкурентний тест; зіставлено початковий і кінцевий стан.

Роботи №1–7 є послідовними окремими реалізаціями: №1 — статичні дані, №2 — форма без збереження, №3 — об'єктна модель, №4 — PDO/MySQL і CRUD, №5 — AJAX та купівля, №6 — API, №7 — оптимізація запитів і кеш. Бази №4–7 окремі. Фінальна версія поєднує API та схему №7 з CRUD-формами №4; попередні роботи не змінювалися.

Початковий стан оцінено статичним аналізом коду. Результати «після» отримано під час фактичного тестування №8. Висновки про відсутність вразливостей стосуються перевірених ділянок і сценаріїв, а не є гарантією безпеки всього застосунку.

## 3. Результати аудиту вихідного коду

Аудит «до» виконаний читанням коду, без атак на старі бази.

- **SQLi:** не знайдено конкатенації користувацьких даних у SQL №4–7. `findByVenue()` №4 вже використовує `prepare/execute`; №5 конкатенує `%` зі значенням параметра, а не з текстом SQL. №6–7 раніше взагалі не мали фільтра venue. У №8 він є і в HTML, і в API.
- **XSS:** №1 виводить title без екранування, але джерело — статичний масив, тому експлуатовану stored XSS не підтверджено. №2 має `h()`, №3–4 — `htmlspecialchars()`, №5 — `textContent`; №6–7 повертають JSON. У №8 всі текстові HTML-поля екрануються з явними ENT_QUOTES та UTF-8.
- **CSRF:** у №4–7 немає перевірок токена. У №2 токена також немає, але форма нічого не зберігає. У №4 `delete.php` змінює БД через GET; JavaScript confirm не захищає прямий запит.
- **Купівля:** у №5–7 уже POST і атомарний UPDATE, тому вразливість купівлі через GET у цих файлах не знайдено. Додано CSRF і захист повторного надсилання форми.
- **Валідація:** №4 перетворює seats_left через `(int)`, приймаючи некоректні рядки як числа. №6–7 використовують `trim()` без перевірки типу, не обмежують довжину title/venue, перетворюють id через `(int)`.
- **Помилки:** №4 `db.php` показує `PDOException::getMessage()`. №6–7 не мають загального обробника помилок SQL. №5 приховує винятки, але не записує їх у лог.

Ціна є лише у статичних даних №1/№3; у формах, API та схемах №4–7 поля price немає. Тому перевірка введення ціни тут не застосовується; нову платіжну модель не додано. Ідентифікаторів замовлення/покупки також немає.

## 4. SQL Injection, XSS, CSRF: payload і виправлення

### SQL Injection

Payload: `' OR '1'='1`. HTML-фільтр використовує точну відповідність venue; API — пошук підрядка LIKE. В обох випадках тест повернув порожній результат, а не всі записи.

```php
$stmt = $pdo->prepare('SELECT * FROM events WHERE venue = :venue ORDER BY event_date');
$stmt->execute([':venue' => $venue]);
```

PDO має `ATTR_EMULATE_PREPARES => false`. `%` та `_` у LIKE залишаються звичайними пошуковими шаблонами; це не SQL-ін'єкція.

### XSS

Payload: `<script>alert(1)</script>`. Збережений через API та повторно прочитаний із MySQL. У списку й атрибуті value форми редагування отримано `&lt;script&gt;alert(1)&lt;/script&gt;`; сирого script-елемента немає. JSON зберігає оригінальний текст без HTML-екранування.

```php
return htmlspecialchars((string)$value, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
```

### CSRF

Payload: POST без csrf_token, `csrf_token=wrong`, повторення попереднього токена після успішної купівлі. Результат: 403, кількість подій та seats_left не змінилися.

```php
$_SESSION['csrf_token'] = bin2hex(random_bytes(32));
// При перевірці обов'язково перевіряється тип token.
if (!is_string($token) || !hash_equals($_SESSION['csrf_token'], $token)) {
    fail(403, 'Недійсний CSRF-токен');
}
```

Форми мають прихований csrf_token. Для JSON API токен передається заголовком `X-CSRF-Token` разом із session cookie; для form-data дозволено csrf_token. Отримати їх можна, відкривши index.php. Після кожної успішної зміни даних токен оновлюється — перед наступним записом треба оновити сторінку. Стара відкрита вкладка отримає 403 до оновлення.

У вихідному API немає автентифікації, Bearer-токенів і користувачів. У №8 CSRF застосовується до всіх POST, оскільки використовується cookie сесії; CORS-доступ стороннім сайтам не відкривається. CSRF не є авторизацією: прямий клієнт може створити власну сесію й змінювати дані. Додавання ролей/власників не входить у наявну функціональність.

## 5. Перевірки GET, повторних запитів, валідації та помилок

Купівля і видалення через GET повертають 405. Успішні HTML POST повертають 303 Location: index.php. Оновлення отриманої GET-сторінки не повторює покупку. Ротація токена та блокування PHP-сесії не дозволяють повторно провести старий POST в одній сесії. Це не загальна ідемпотентність платежів: новий токен означає нову дозволену покупку.

```sql
UPDATE events SET seats_left = seats_left - 1
WHERE id = ? AND seats_left > 0
```

Наявність місць перевіряється самим атомарним UPDATE. Нуль змінених рядків відхиляє покупку. Окремі клієнти не можуть зменшити залишок нижче нуля.

Сервер перевіряє типи, непорожні title/venue, довжину до 255 символів, реальну дату, ціле seats_left від 0 до 4294967295 та правильний id. Відхилення — 400. Помилки PDO/Throwable записуються через error_log(), користувач отримує загальне повідомлення та 500. Для відсутньої події API повертає 404; методів поза контрактом — 405. Збережено 201 при створенні, 200 при читанні/купівлі та початковий 400 API при відсутності квитків; HTML-покупка повертає 409.

Кеш soldout №7 з TTL 60 секунд збережено та відокремлено від кешу №7; усі шляхи зміни даних його очищають. Кеш — лише для читання, рішення про покупку завжди приймається в MySQL.

## 6. Результати перевірок до/після

Фактично виконано 22.11.2026 на PHP 8.5.10, MySQL 26.7.0, окремій тестовій базі MySQL.

| Перевірка | До (аналіз коду) | Після (виконано) |
|---|---|---|
| php -l | Не запускався для архівів | Усі PHP-файли №8 без синтаксичних помилок |
| PDO, список, venue | Підготовлені запити вже були | HTTP 200, фільтрація працює |
| SQLi payload | Вразливість не виявлена | HTML/API не повертають чужі результати |
| XSS payload | Експлуатована XSS не підтверджена | Збереження в MySQL; HTML екранований, JSON незмінений |
| CSRF | Токенів немає | Відсутній/неправильний/використаний токен → 403 |
| Дані після 403 | Захисту немає | Кількість записів та залишок незмінні |
| GET | Видалення №4 небезпечне; купівля №5–7 вже захищена методом | buy/delete/API buy → 405 |
| Купівля | Умовний UPDATE уже був | Залишок 2 → 1 → 0, наступна покупка відхилена |
| Повторне надсилання | Немає токена | Старий POST → 403; refresh не змінює залишок |
| Валідація | Некоректні типи/касти | Порожня назва, -1, 1.5, неіснуюча дата → 400 |
| CRUD | Без CSRF | Редагування/видалення → 303; без токена → 403 |
| Конкуренція | Атомарний SQL уже був | 8 окремих PDO-процесів: рівно 1 успіх, залишок 0 |
| Помилка БД | №4 показує виняток | Реальна помилка підключення до відсутньої БД → 500 без деталей |

XSS перевірено аналізом фактичних HTML-відповідей, без автоматизованого запуску JavaScript у браузері. Конкурентний тест перевіряє той самий SQL через окремі PDO-з'єднання, а не паралельні HTTP-запити до однопотокового php -S. Старі програми не запускалися проти їхніх робочих баз. Жодних старих записів не видалено.

## 7. Висновок

Під час аудиту виявлено відсутність CSRF-перевірок, видалення через GET у практичній №4, недоліки серверної валідації та розкриття технічних помилок. У фінальній версії ці недоліки усунуто: операції зміни даних перевіряють токен, видалення й купівля потребують POST, вхідні дані перевіряються на сервері, а винятки журналюються без розкриття деталей користувачу.

У перевірених SQL-запитах №4–7 ін'єкцій не виявлено: підготовлені запити вже застосовувалися. Купівля у №5–7 також уже використовувала POST та атомарний UPDATE. Експлуатовану XSS у вихідних версіях не підтверджено; у №8 явне екранування перевірено на збереженому payload. Ці результати відокремлено від реально знайдених недоліків.

Фактичні перевірки підтвердили відхилення неправильних CSRF-токенів без зміни даних, захист від повторного надсилання старої форми, безпечну обробку цільових SQLi/XSS-payload та неможливість від'ємного залишку під час конкурентної купівлі. Автентифікація, ролі й платіжні операції не входять до реалізованої моделі.
